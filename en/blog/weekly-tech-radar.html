Weekly Tech Radar: I Automated My Tech Watch, Then I Broke It

July 25, 2026 7 min read
Project DevOps AI

27 sources. 300 articles to sort through every week. A 10-minute read at the end.

One Saturday, everything broke.

And it's entirely my fault.

But before I get into that, here's the project.

The project: my tech watch on autopilot

I wanted to keep up with cloud, DevOps and AI without burning my evenings on it. The problem isn't a lack of information, it's the opposite. Twenty-seven feeds spit out around 300 articles a week. Reading them all is impossible, ignoring them all is worse. What's missing isn't content, it's curation.

Weekly Tech Radar is the pipeline that does that sorting for me. Every Saturday at 8am, it collects those 300 articles, keeps the most relevant ones, summarizes them in French and English, and publishes an edition on my portfolio. All for a few cents a week, without me opening my terminal.

It's been running for four months, one edition every Saturday, nineteen so far. The code is public at github.com/TuroTheReal/weekly-tech-radar, and the editions are online at arthurbernard.dev/en/tech-radar.

Why a tech watch, and why like this

Tech watch is part of the job. Cloud, DevOps and AI move every month: a managed service changes its pricing, a critical CVE drops, a tool becomes the new standard. Not keeping up means falling behind without even noticing. For someone aiming at architecture, knowing what's going on is part of the work, not a bonus.

The trap is volume. Subscribing to twenty-seven feeds is easy. Reading them isn't. At first I'd scroll, bookmark, and never come back. Tech watch without curation is just anxiety with an RSS feed.

Hence the choice of RSS and Atom over an algorithm-driven feed. No opaque recommendations, no content pushed for engagement, no manufactured FOMO. I pick my sources and I keep them. Twenty-seven feeds across six domains: cloud, devops, security, ai, business, tech. French and English, because the two ecosystems don't talk about the same things at the same time.

The editorial line is hardcoded into the prompt: Factual only: no opinions, no editorial. I don't want a summary that comments, I want the fact and its concrete impact. The prompt even gives Claude the example, bad versus good:

BAD:  "Report on the state of open source on Hugging Face"
GOOD: "Hugging Face downloads grew 60% in 6 months, driven by diffusion models"

A fact, a number, an impact. That's what I want to read on a Saturday, not one more opinion.

And there's one line I don't move. The AI sorts, deduplicates, summarizes. It doesn't decide what gets published. The pipeline opens a Pull Request, I review, I merge. The sorting is automatic, the editorial stays human.

How it works

Three Python scripts, orchestrated by a GitHub Actions cron. Nothing more.

Collect. collect.py parses the 27 RSS and Atom feeds (AWS, Kubernetes, CNCF, GitHub, TechCrunch and others) and keeps articles from the last 7 days. Around 300.

Select and summarize. summarize.py sends those 300 articles to Claude Haiku, Anthropic's small, fast and cheap model. The model runs three passes: it selects the 40 most relevant for a cloud/DevOps profile, removes duplicates (about thirty remain), then writes a factual FR and EN summary for each before filing it into one of six categories.

Publish. publish.py clones the portfolio repo, generates the bilingual HTML pages, updates the listing and homepage cards, opens a Pull Request. Netlify builds a deploy preview. I review, I merge. Live.

GitHub Actions (Saturday 8am UTC)
        |
   collect.py    27 RSS feeds ->  ~300 raw articles
        |
  summarize.py   Claude Haiku ->  top 40 -> dedup ~35 -> FR+EN summaries
        |
   publish.py    generates HTML -> opens a PR on the portfolio
        |
     Netlify     deploy preview

The pipeline is idempotent: I can re-run it safely, it skips weeks already processed. That's what saved me that Saturday.

The Saturday it all crashed

Two weeks in production. Barely enough time to feel safe. Then one Saturday morning, GitHub Actions notifies me: the workflow exits with exit code 1. The summarize step. No edition generated.

The error message wasn't about the API, the network, or a quota. It was about JSON.

Here's what happened. My prompt asked Claude to summarize the thirty-odd selected articles in one go, each with a translated title, two summaries and a category, all in a single JSON response my script then parses. Two instructions, written plainly in the prompt:

Summarize ALL articles without exception.
Respond with ONLY valid JSON.

That week, the selection was dense. The expected response exceeded my token budget: I'd set max_tokens to 8192. Claude wrote up to the limit, then stopped. Mid-JSON. My parser got an object cut clean off, invalid, impossible to load.

The real culprit wasn't Claude. It was me, on two counts.

First, I'd assumed an instruction in a prompt was a guarantee. "Respond with valid JSON" doesn't bound the length of the output, and "summarize everything without exception" pushes it right past the limit. A prompt describes an intention, it doesn't sign a contract. An LLM's output is external data: non-deterministic, unbounded. I was treating it like a reliable return value from my own code.

Second, my parser was lying. When it didn't find usable JSON, it didn't raise an error: it silently restarted from the beginning of the text, with a default value.

# The buggy version: default=0 hides the missing JSON
start = min((text.find(c) for c in '[{' if text.find(c) != -1), default=0)

That default=0 masked the problem for weeks instead of flagging it. The day the truncation was clean, the failure blew up all at once, with no clear lead.

The fix, and what I take away

Three fixes, in this order of priority.

First, fail loudly. If the response contains no usable JSON, the script raises an explicit error with the start of the text it received. A bug you can see beats a silent bug a thousand times over.

candidates = [text.find(c) for c in '[{' if text.find(c) != -1]
if not candidates:
    raise ValueError(f"No JSON found in response: {text[:200]}")
start = min(candidates)

Then, a retry loop. A model's output isn't deterministic: the same request can succeed on the second try. Three attempts before giving up. And along the way, max_tokens from 8192 to 16384: more headroom. That pushes the ceiling back, it doesn't remove it. The real lesson isn't in that number.

for attempt in range(3):
    response = client.messages.create(
        model="claude-haiku-4-5-20251001",
        max_tokens=16384,          # was: 8192
        messages=[{"role": "user", "content": prompt}])
    try:
        return extract_json(response.content[0].text)
    except (json.JSONDecodeError, ValueError) as e:
        print(f"Attempt {attempt + 1}/3 failed: {e}")
        if attempt == 2:
            raise

The real lesson is that I treated a probabilistic component like a deterministic one. We learn to validate user input, to handle network timeouts, to never trust a third-party API without a guardrail. An LLM's output demands exactly the same discipline: validate, bound, retry, fail loud. A prompt isn't a promise.

Since the pipeline is idempotent, a simple re-trigger regenerated the missing edition once the fix was pushed. No data lost. The crash cost me half an hour and a good lesson.

And now

The radar is still running. Every Saturday, without me, it turns 300 articles to sort through into a 10-minute read.

What it changed, concretely: I went from a patchy tech watch, done when I remembered, often never, to a systematic one I actually read. Ten minutes on the weekend, and I know what moved in cloud, DevOps and AI. Not everything. The essentials, filtered for my profile. It's the difference between drowning in thirty open tabs and reading one page that gets to the point.

And since the editions stay archived on the portfolio, I also have a record. Months later, I can trace a topic back, see which week a given tool first showed up on the radar. A tech watch that keeps, not just one that scrolls by.

If this speaks to you, this week's edition is at arthurbernard.dev/en/tech-radar. And if you want to build one for your own tech watch, the repo is public and documented at github.com/TuroTheReal/weekly-tech-radar.

A prompt isn't a guarantee. But framed properly, it can run a tech watch on its own for months.
